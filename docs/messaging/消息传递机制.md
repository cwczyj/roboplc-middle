# 消息传递机制

> RoboPLC 使用 Hub 消息总线实现 Worker 之间的消息传递。本文档详细说明消息类型、传递流程和设计决策。

## 🔄 消息类型

### DeviceControl

设备控制请求消息，用于控制 Modbus 设备。

**字段：**
```rust
pub struct DeviceControl {
    pub device_id: String,          // 目标设备 ID
    pub operation: Operation,       // 操作类型
    pub params: JsonValue,          // 操作参数
    pub correlation_id: u64,        // 请求 ID，用于匹配响应
    pub respond_to: Option<Sender<DeviceResponseData>>, // 直接响应通道
}
```

**操作类型：**
- `ReadSignalGroup`：读取信号组
- `WriteSignalGroup`：写入信号组
- `GetStatus`：查询设备状态

### DeviceResponse

设备控制响应消息，包含操作结果。

**字段：**
```rust
pub struct DeviceResponse {
    pub device_id: String,          // 目标设备 ID
    pub success: bool,              // 操作是否成功
    pub data: JsonValue,            // 操作结果数据
    pub error: Option<String>,      // 错误信息（如果有）
    pub correlation_id: u64,        // 请求 ID，匹配原始请求
}
```

### DeviceResponseData

设备响应数据类型别名，用于直接响应机制。

```rust
pub type DeviceResponseData = (bool, JsonValue, Option<String>);
// 元组结构：(success, data, error)
```

### ConfigUpdate

配置更新通知消息，由 ConfigLoader 发送。

**字段：**
```rust
pub struct ConfigUpdate {
    pub config: String,  // JSON 格式的配置内容
}
```

### DeviceHeartbeat

设备心跳消息，由 HeartbeatWorker 广播。

**字段：**
```rust
pub struct DeviceHeartbeat {
    pub device_id: String,       // 设备 ID
    pub timestamp_ms: u64,       // 时间戳（毫秒）
    pub latency_us: u64,         // 延迟（微秒）
}
```

### TimeoutCleanup

超时清理消息，由 RpcWorker 发送给 DeviceManager，用于清理超时请求。

**字段：**
```rust
pub struct TimeoutCleanup {
    pub correlation_id: u64,     // 超时请求的关联 ID
}
```

### SystemStatus

系统状态查询消息，由 HttpWorker 发送。

**字段：**
```rust
pub struct SystemStatus {
    pub requester: String,                           // 请求者标识
    pub respond_to: Sender<SystemStatusResponse>,    // 响应通道
}
```

### SystemStatusResponse

系统状态响应结构体。

**字段：**
```rust
pub struct SystemStatusResponse {
    pub devices_count: u32,      // 设备总数
    pub system_healthy: bool,    // 系统健康状态
    pub uptime_secs: u64,        // 运行时间（秒）
}
```

## 📡 消息传递流程

### 1. RPC Worker → Modbus Worker（直接响应架构）

**架构演进说明：** 新架构不再通过 DeviceManager 路由 DeviceControl/Response 消息，ModbusWorker 直接使用 respond_to 通道响应给 RpcWorker。

```
RPC Worker
    │
    ├── 接收 JSON-RPC 请求
    │
    ├── 解析请求并生成 DeviceControlRequest
    │
    ├── 生成唯一 correlation_id（原子递增计数器）
    │
    ├── 创建 oneshot 通道用于接收响应
    │
    ├── 通过内部 mpsc 通道发送 DeviceControlRequest
    │
    └── Bridge 任务将请求转换为 Message::DeviceControl
    │
    └── 通过 Hub 发送 DeviceControl 消息
    │
    └── 等待 oneshot 通道响应（带 30 秒超时）
    │
    └── 超时时发送 TimeoutCleanup 消息
    │
    └── 将结果转换为 JSON-RPC 响应返回客户端
```

**关键点：**
- **双通道机制**：RpcWorker 使用 `mpsc` 通道在 RpcHandler 和主循环间传递请求，使用 `oneshot` 通道接收响应
- **直接响应**：`respond_to` 字段包含 oneshot 发送端，ModbusWorker 直接响应
- **超时处理**：请求超时时发送 `TimeoutCleanup` 消息清理 `pending_requests`

### 2. Hub 路由

```
Hub
    │
    ├── 接收来自 RPC Worker 的 DeviceControl
    │
    ├── ModbusWorker 接收并处理
    │   │
    │   ├── 验证 device_id 匹配
    │   │
    │   ├── 执行 Modbus 操作
    │   │
    │   └── 直接通过 respond_to 发送响应
    │       （不再经过 DeviceManager 路由）
    │
    └── DeviceManager 订阅 TimeoutCleanup 消息
        │
        └── 清理 pending_requests
```

**关键点：**
- **直接响应**：ModbusWorker 直接使用 respond_to 通道发送响应，无需 DeviceManager 路由
- **DeviceManager 职责变化**：现在只处理 TimeoutCleanup 消息，用于清理超时请求

### 3. TimeoutCleanup 处理

```
RpcWorker 检测到请求超时
    │
    └── 发送 Message::TimeoutCleanup { correlation_id }
    │
    └── DeviceManager 接收
    │
    └── 从 pending_requests 中移除对应条目
    │
    └── 记录清理日志
```

### 4. DeviceHeartbeat 消息流

```
HeartbeatWorker
    │
    ├── 轮询检测设备状态
    │
    ├── 发送 GetStatus DeviceControl 请求
    │
    ├── 记录延迟
    │
    ├── 更新 device_states
    │
    └── 广播 DeviceHeartbeat 消息
        │
        └── LatencyMonitor 接收
            │
            ├── 维护延迟统计窗口
            │
            ├── 3-sigma 异常检测
            │
            └── 发送延迟异常事件
```

### 5. Hub 消息订阅

Hub 使用 `event_matches!()` 宏选择特定消息类型：

```rust
// DeviceManager 订阅（仅 TimeoutCleanup）
event_matches!(Message::TimeoutCleanup { .. })

// ModbusWorker 订阅
event_matches!(Message::DeviceControl { .. })

// LatencyMonitor 订阅
event_matches!(Message::DeviceHeartbeat { .. })

// ConfigUpdater 订阅
event_matches!(Message::ConfigUpdate { .. })
```

**消息投递策略：**
- `#[data_delivery(always)]` - 消息总是投递到所有订阅者（广播）
- `#[data_delivery(single)]` - 消息只投递到一个订阅者（单播）

## 📊 请求-响应生命周期

### 请求创建

```
1. RPC Worker 收到 JSON-RPC 请求
2. 生成 correlation_id（原子递增计数器）
3. 创建 oneshot 通道 (tx, rx)
4. 构建 DeviceControlRequest { ..., respond_to: tx }
5. 通过 mpsc 通道发送到 bridge 任务
6. Bridge 创建 Message::DeviceControl 并发送到 Hub
```

### 请求处理

```
1. Hub 投递 DeviceControl 到 ModbusWorker
2. ModbusWorker 验证 device_id
3. 执行 Modbus 操作
4. 直接通过 respond_to 发送响应
```

### 响应处理

```
1. ModbusWorker 完成操作
2. 直接通过 respond_to.send() 发送响应给 RpcWorker
3. RpcWorker 的 response_rx 接收到响应
4. 转换为 JSON-RPC 响应返回客户端
```

### 超时处理

```
1. RpcWorker 的 response_rx 等待超时（30 秒）
2. 发送 Message::TimeoutCleanup { correlation_id } 到 Hub
3. DeviceManager 接收并从 pending_requests 移除条目
4. 记录超时警告日志
5. 向客户端返回超时错误
```

### 错误处理

```
1. 操作失败时 ModbusWorker 通过 respond_to 发送错误响应
2. RpcWorker 将错误包装为 JSON-RPC 错误响应
3. 记录详细的错误日志
```

## 🎯 设计模式

### 1. 直接响应机制

使用 `respond_to: Option<Sender<DeviceResponseData>>` 实现直接响应：

**优势：**
- 避免 DeviceManager 路由开销
- 消除消息循环风险
- 简化架构
- 提高响应速度

### 2. 非阻塞设计

- RpcWorker 使用 tokio 异步运行时
- 使用 `tokio::select!` 实现并发处理
- 使用 `oneshot` 通道等待响应
- 使用 `std::sync::mpsc` 桥接同步和异步代码

### 3. 背压控制

ModbusWorker 的 `max_concurrent_ops` 配置限制最大并发操作数。

### 4. 优雅降级

连接失败时使用指数退避策略，避免重连风暴。

### 5. 状态机

ModbusWorker 维护连接状态、心跳时间、操作统计。

## 🔧 配置管理

### 消息类型定义

```rust
#[derive(Clone, Debug, DataPolicy)]
pub enum Message {
    #[data_delivery(single)]
    DeviceControl { ... },
    DeviceResponse { ... },
    #[data_delivery(always)]
    DeviceHeartbeat { ... },
    #[data_delivery(always)]
    ConfigUpdate { ... },
    TimeoutCleanup { ... },
    SystemStatus { ... },
}
```

### worker_map 初始化

DeviceManager 从配置加载设备时创建 worker_map：

```rust
for device in &config.devices {
    worker_map.insert(device.id.clone(), format!("modbus_worker_{}", device.id));
}
```

### 配置热更新流程

```
1. ConfigLoader 检测到配置文件变化
2. 解析新配置（JSON 差异）
3. 通过 Hub 广播 ConfigUpdate 消息
4. ConfigUpdater 接收并应用更新
   - 更新设备列表（添加/移除）
   - 更新 device_states
   - 更新 worker_map
   - 必要时重启 ModbusWorker
```

## 📚 并发安全

### Hub 消息投递

Hub 使用非阻塞投递（try_send），高优先级消息不会被阻塞。

### Worker 消息处理

每个 Worker 的 run() 方法顺序处理消息：
1. 验证消息类型和来源
2. 执行相应操作
3. 发送响应

### 共享状态访问

使用 `parking_lot_rt::RwLock` 实现实时安全的共享状态访问：

```rust
pub struct Variables {
    pub device_states: Arc<RwLock<HashMap<String, DeviceStatus>>>,
    pub latency_samples: DataBuffer<LatencySample>,
    pub device_events: DataBuffer<DeviceEvent>,
}
```
